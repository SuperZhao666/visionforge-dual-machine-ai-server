# VisionForge QNN HTP benchmark

The Android arm64 product ships four 416x416 W8A16 models for Qualcomm QNN HTP and
hash-pinned portable ONNX models for the explicit NNAPI/CPU compatibility route. The
repository also retains a historical 320x320 native benchmark for toolchain comparison.
These backends remain separate evidence domains: `SessionOptions.addNnapi()` is not
evidence of Hexagon execution, and a portable fallback is never reported as QNN HTP.

## Build

```powershell
$sdk = "$PWD\qnn_sdk\qairt\2.37.1.250807"
& .\gradlew.bat --no-daemon :app:assembleDebug "-PqnnSdkRoot=$sdk"
```

The build stages the required arm64 QNN runtime closure: HTP backend, HTP prepare library,
V68/V69/V73/V75/V79 stubs and DSP skeletons, plus the four approved 416x416 W8A16 model
libraries. QAIRT `2.37.1.250807` does not contain a V81 stub/skeleton pair. A V81 device is
therefore not an HTP-certified production target until the SDK, packaged closure, models and
physical-device evidence are upgraded together. Its QNN candidate fails closed; the separate
portable NNAPI and CPU candidates may proceed only after their own model-integrity,
initialisation and real graph-execution checks succeed.

Architecture staging discovers strict `libQnnHtpV<digits>Stub.so` and matching skeleton pairs
from the selected SDK instead of maintaining a future-version allowlist. Release verification
still requires the V68/V69/V73/V75/V79 baseline. Set
`VISIONFORGE_REQUIRED_QNN_HTP_ARCHITECTURES` to raise that release floor; requesting V81 with
the current SDK fails the build before an APK can be published.

The selected SDK is also bound to the approved models. The build reads `version` and
`build_id` from the SDK's `sdk.yaml`, compares the normalized identity with the approved model
manifest, and verifies the full embedded `QNN_SDK_VERSION` in all four model libraries. A
newer V81 runtime cannot be mixed with models generated by QAIRT 2.37.1; the four models must
be rebuilt and reapproved with the same newer SDK before the release gate can pass.

## Required Android contract

- The manifest declares `libcdsprpc.so` as a vendor public native library.
- `ADSP_LIBRARY_PATH` uses semicolon separators. This is the FastRPC convention and differs
  from `LD_LIBRARY_PATH`.
- The app extracts and verifies every packaged HTP skeleton in its private files directory
  before creating the QNN backend.
- The UI may report QNN ready only after backend, device, context, graph composition and graph
  finalisation succeed. An unsupported Snapdragon/HTP generation is terminal for that QNN
  candidate. Portable fallback is a separate compatibility path and must expose its actual
  `onnxruntime_nnapi` or `onnxruntime_cpu` backend after one real graph execution; it must never
  inherit an HTP readiness or performance claim.

## Current production model set

- `libvalorant_416_v11s_no_flash_w8a16.so`
- `libow2_416_w8a16.so`
- `libdelta_416_v8s_w8a16.so`
- `libcs2_vombit_416_v8s_w8a16.so`

The CS2 Vombit model is maintained as a project-owned private model artifact. Its local
integration and phone HTP numeric contract are approved, and private Release builds use
the same model hash closure as integration builds.

Packaging an HTP architecture is only build compatibility. Physical certification remains
per phone and firmware as defined in `../docs/DUAL_MACHINE_SNAPDRAGON_COMPATIBILITY.md`.

## Device benchmark bundle

Create every device bundle with the same SDK whose runtime it will execute:

```powershell
.\tools\prepare_qnn_htp_device_bundle.ps1 -QnnSdkRoot $sdk -RuntimeInput <input.raw>
.\tools\run_qnn_htp_adb.ps1
.\tools\analyze_qnn_htp_profile.ps1 -QnnSdkRoot $sdk
```

Preparation discovers complete HTP stub/skeleton pairs from that SDK and records both the
architecture list and the SDK's `QnnTypes.h` SoC mapping in `manifest.json`. The ADB runner
uses only this bundle-bound mapping; it never searches another installed SDK. Rebuild an old
bundle before running it if its manifest does not contain `soc_models`. Preparation also
requires the model library's embedded full QAIRT build identity to match the selected
`sdk.yaml`; a newer runtime cannot be benchmarked with an older generated model. Known
Snapdragon requirements come from `qnn_htp_soc_architectures.json`; the runner rejects a known
device before ADB push when its required architecture is absent, while unknown SoCs still
continue to the QNN backend's real capability probe.

## Historical 320x320 benchmark evidence (not the current shipping model)

- QNN W8A16 NHWC graph: `libvalorant_320_v11n_int8.so`
- Exact split-output export: coordinates `[1,4,2100]` and confidences `[1,2,2100]`
- QNN HTP / Hexagon V75
- DCVS v3 bus and core: `TURBO_PLUS`
- HTP sleep disabled during the active inference session
- RPC control latency: 100 microseconds
- 30 warm-up + 300 measured native `graphExecute` calls

The selected App-native run measured 1.43 ms mean, 1.40 ms median (714 FPS), and 1.59 ms P95.
It uses a 614,400-byte UINT16 input buffer and two FP32 output buffers totaling 50,400 bytes.
The benchmark mutates its input and records output fingerprints, so the result is not a stale
output-buffer measurement. QNN detailed profiling separately proves HTP/HVX/HMX execution.

The original all-U8 output graph produced an attractive 0.68 ms median but is explicitly
rejected for deployment: one U8 encoding covered both 0--320 coordinates and 0--1 confidences,
which collapsed useful confidence values to zero. The split-output ONNX rewrite is algebraically
exact in FP32; its W8A16 QNN result on the checked 320x320 image has cosine 0.999844 versus
FP32 and identical candidates at the 0.25 confidence threshold (3 of 3). A labeled validation
set is not present in this repository, so this is a numerical-equivalence gate, not a claimed
mAP or recall measurement.

The device-side QNN detailed profile for this same graph records four HVX threads in use, zero
HTP yields, explicit HVX/HMX power acquisition, and QNN accelerator execution events. This is
separate evidence that the graph reaches the Hexagon HTP execution path; the app audit proves
that the production JNI path loads FastRPC, the V75 skeleton, and executes that graph.

### Rejected quantization candidates

QNN 4-bit weights were evaluated as a speed candidate on the same device. Packed 4-bit weights
failed QNN graph composition because the generated static tensor payload did not match its 4-bit
shape. The unpacked 4-bit variant ran, but its dequantized output versus the accepted INT8
candidate was only 0.9917 cosine similarity (MAE 7.47 on the checked output), and three equal
300-call device runs were not faster (INT8: 1053--1148 ms; 4-bit: 960--1311 ms). Both are
therefore excluded from the runtime until a new QNN toolchain and a full detection-quality
evaluation demonstrate a genuine gain.

An explicit 8 MB VTCM graph reservation was also accepted by the HTP backend but measured
0.82 ms mean in the native App benchmark, slower than the default allocator. The shipping
configuration deliberately leaves VTCM allocation to the QNN HTP backend.

HTP static-weight packing was likewise accepted and audited, but measured 0.85 ms mean. It is
also slower than the default generated INT8 graph layout and is not enabled.

The 714 FPS figure is pure native graph execution only. It excludes camera/screen capture,
image conversion, post-processing, control logic, UI, and transport. Those must be benchmarked
as a separate end-to-end pipeline before making an application-level FPS claim.
